# Feature: the learner confirms the generated knowledge map

Lane P1 (contract) with P2 (service, done), P3 (route), P5 (screen). Status: **contract proposed by P1 on 2026-11-07,
additive, pending P3's and P5's agreement**; P2's backend already exists (`specs/p2-graph-confirmation/handoff.md`).

## Why
The map is generated by a model from textbook chunks, and the demo labels it "Bản nháp tự động — chưa được giáo viên
duyệt". The learner should see the map they are about to be assessed on and accept it before practice. The backend
already refuses practice, attempts and hints (409) until that acceptance exists, so the web and the route need one
shared, unambiguous shape.

## The contract (decided here, in `app/schemas.py`)
- `GET /graph` gains `revision`: an **opaque** string (1-128 chars) identifying the map the response was projected
  from. The real route always sets it; it is `None` only in legacy stubs. Nobody parses it.
- `POST /graph/confirm` takes `GraphConfirm {learner_id, subject, revision}` and returns `GraphConfirmed
  {confirmed, revision}`. `revision` is **required**: there is no "confirm the latest".
- Errors (HTTP, not new models): **409** the revision is stale (the map changed since the learner saw it; fetch the
  graph again and show it); **404** unknown learner or topic; **422** invalid body; **503** graph unavailable.
- Until a learner has confirmed the current revision, `POST /attempts`, `POST /tutor/hint` and the practice routes
  return **409**. The same status means different things on different routes; the client tells them apart by route.

## Behaviour that must hold (from P2's service)
1. Confirmation is **explicit**, a separate user action, never a side effect of reading the graph.
2. The revision confirmed is the one the learner was shown: P5 keeps the revision from the same `GET /graph`
   response it displayed.
3. A change to the graph removes acceptance, including changing back to a previously accepted graph. Replaying an
   identical graph keeps it.
4. Confirmation changes no mastery, no item status, no placement and no job.
5. Identity comes from the authenticated boundary, **not** from a learner id typed in by the browser, and the shared
   API key is not a per-learner identity. For the demo (one learner, no login) the boundary names that learner.

## Out of scope
Login and real per-learner identity (after the contest); editing the map; a separate "reject" action (the learner
leaves instead); the 409 body format beyond a Vietnamese `detail` string.

## Acceptance
- Contract tests in `tests/engine/test_contracts.py` and regenerated mocks (`specs/contracts/mocks/graph-confirm.*`,
  `graph.response` with a revision) pass.
- Through the real routes: confirm with the shown revision gives 200 and practice then works; confirm with an old
  revision gives 409; practice before confirming gives 409. Step 2a of `specs/contracts/h7-run-sheet.md` covers this.
